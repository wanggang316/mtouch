# Design Docs

Design docs record the **why** and **how** behind features and systems.

## When to Write a Design Doc

- A new feature or system touching several domains
- A significant architectural change
- A technical decision with long-term consequences
- Any work where multiple approaches exist and the choice matters

Not every change needs one. Most of this project's decisions are recorded where
they are enforced — as a validation-contract assertion, or as the comment next to
the code that implements them. Write a design doc when the reasoning is larger
than the diff.
